# План выступления на 5–6 минут

Основан на вопросах из «Основные вопросы для защиты по ПМ 6.docx». Здесь план и ответы, а не готовая презентация. Не называйте проект коммерческой мастерской и не заявляйте непроверенные функции.

## 1. Представление — 40 секунд

«Мой проект — RepairLab, учебный сайт записи на диагностику техники, и приложение оператора RepairLab на Python. Клиент выбирает устройство и оставляет заявку, оператор видит её и меняет статус».

Покажите `screenshots/desktop.png`. Цель — связать действия пользователя на фронтенде с обработкой на бэкенде.

## 2. Python-приложение — 50 секунд

Запустите `python operator_app.py`. Покажите таблицу, выберите заявку, измените статус и экспортируйте CSV. Сделайте собственный скриншот окна: графический интерфейс в рабочей среде автоматически не проверен.

Библиотеки: tkinter и ttk для окна; sqlite3 для БД; csv для экспорта. Класс `OperatorApp` наследует `tk.Tk`. Методы: `refresh`, `show_detail`, `update_status`, `export`. `Treeview` показывает строки, `Combobox` выбирает статус, `messagebox` выдаёт сообщения.

Фрагмент для объяснения из `update_status`:

```python
with connect() as conn:
    conn.execute('UPDATE requests SET status=? WHERE id=?',
                 (self.status.get(), selected[0]))
self.refresh()
```

«Получаем выбранный статус и номер строки, передаём их параметрами SQL, фиксируем изменение и обновляем таблицу».

## 3. Frontend — 50 секунд

Страницы: главная и обработка данных. HTML задаёт семантическую структуру, CSS — сетки, цвета и медиазапросы, JavaScript — фильтрацию и отправку формы. JS-фреймворков нет: код проще разобрать на защите. Покажите разные карточки и фильтр, затем `screenshots/mobile.png` и мобильный режим DevTools. Объясните переход четырёх колонок в две и форму в одну колонку.

## 4. Backend — 60 секунд

Покажите `app.py`, функции `application`, `validate`, `connect`. Язык Python, интерфейс WSGI; локально стандартный `wsgiref`, при размещении Gunicorn. В DevTools → Network отправьте форму и откройте POST `api/requests`: Payload → JSON, Response → номер, статус 201.

Цепочка: действие пользователя → fetch POST → WSGI-маршрут → проверка → INSERT SQLite → HTTP 201 JSON → сообщение в браузере.

## 5. Данные и безопасность — 50 секунд

Данные в `data/requests.sqlite3`. Таблица `requests`: номер, имя, телефон, услуга, дата, описание, время создания, статус. Добавление через INSERT, чтение через SELECT в приложении оператора. Проверка выполняется на клиенте и сервере. Параметры SQL защищают структуру запроса; сообщения вставляются через textContent. Публичного списка заявок нет. Вход не реализован: оператор локальный, доступ определяется доступом к компьютеру и базе.

## 6. Результаты — 60 секунд

Сначала отправьте пустую форму: покажите ошибки. Затем заполните тестовые данные, отправьте, покажите номер заявки и ту же запись в операторе после «Обновить». Покажите `screenshots/validation.png` и `screenshots/success.png`. Для проверки именно серверной ошибки в DevTools Console:

```javascript
fetch('api/requests', {
  method: 'POST',
  headers: {'Content-Type':'application/json'},
  body: JSON.stringify({name:'Я',phone:'abc',service:'x',visit_date:'2000-01-01',problem:'x',consent:false})
}).then(async r => console.log(r.status, await r.json()))
```

Будет HTTP 422 с ошибками полей; запись не добавляется. Покажите результат `python -m unittest discover -s tests -v`.

Трудности: связать форму и сервер, обеспечить сохранение данных, отобразить серверные ошибки и перестроить интерфейс на телефоне. Развитие: авторизация удалённого оператора, резервные копии, ограничение спама и уведомления. Эти функции пока не реализованы.

## Перед защитой

Используйте вымышленные данные. Запустите оба приложения заранее. Проверьте доступность порта и шрифт/масштаб VS Code. Подготовьте 6 слайдов по этому плану, с собственным скриншотом Python-приложения. Для надёжной демонстрации используйте локальный сервер; публичную ссылку показывайте только после успешной проверки хостинга. Изучите код и объясняйте его своими словами.
